How the forecasting methods differ

DemandIQ asks two questions. 1 · How does each road grow? 2 · How do road forecasts become turning movements? Any answer to 1 works with any answer to 2.

1 · How each road grows

Worked example (ODOT's own numbers): today's peak-hour count on Main St northbound is 1,690. The model, brought to your years, goes 1,195 → 1,390 (+16 %). Peak-hour factor K = 1 for simplicity.

2 · How road forecasts become turning movements

NCHRP standard — turns per intersection, then balance

Each intersection keeps today's turn pattern, scaled to its own forecast approach and exit totals (Furness). Then a balancing pass makes neighbours agree. This is what NCHRP 765 §6.4 + §6.9 describe and what reviewers expect.

Int 2 eastbound approach forecast 940, Int 1 eastbound exit forecast 905 → balancing settles the link between them.

Use for any study — it's the documented standard. Works for one intersection, corridors and grids.

Trip table — Fratar

First works out today's trips through the corridor (where they enter → where they leave) that reproduce your balanced counts. Then grows them so each end and side street sends and receives its forecast total (the Fratar growth-factor method), and adds the trips up into turns. Neighbours agree by design — no balancing pass.

If the west end grows 10 % and Int 3's north leg grows 30 %, the "west end → Int 3 north" trips grow by about 20 % (both ends' factors).

Use for one straight corridor. It uses only the end and side-street forecasts, so a bad model number on the main street can't leak in — but it also ignores what the model says about the main street itself (e.g. traffic shifting to a parallel road).

Trip table — fuzzy (Visum-style)

Starts from the Fratar trip table, then nudges it so every leg — main street included — lands within ± the band of its own forecast. Each forecast counts as "about right", the way PTV Visum's TFlowFuzzy treats counts. Where all legs already agree, it equals Fratar.

Use for one straight corridor where you also trust the model on the main street. Wider band = closer to Fratar; band 0 = every leg forced exactly.

Furness / Fratar: NCHRP 255 pp. 105–108, NCHRP 765 §6.4. Trip-table estimation from counts: NCHRP 765 §6.11–6.12 (Van Zuylen & Willumsen). Fuzzy bands: PTV Visum TFlowFuzzy (PTV FAQ; ADOT/MAG I-10/SR-101L study, ±5 %).

Test results on a made-up corridor with a known answer

We built a 4-intersection corridor where the true 2045 traffic is known, a fake regional model of it (each road off by ±25 %, like a real model), and today's counts (±5 % count error, balanced the normal way). Then ran every combination, 20 random versions of each scenario. The number is the share of future turning movements within GEH 5 of the truth (higher is better); the small number is the typical error on approach totals.

What it shows

Ratio is the safest road method when there is a model: the model's own error cancels out. Difference does worst when the model is off — in line with NCHRP 765.

The trip-table methods scored higher than the per-intersection standard on this straight corridor. The reason is mostly the model's noise: Fratar reads only the end and side-street forecasts, so random errors on the main-street links never reach it. Given perfect road forecasts instead, the per-intersection standard reproduces the true turns better than Fratar (independent checker, Nov 2026). So the trip tables win when the model is noisy link by link, not because their turn patterns are better.

Trend and entered rate are excellent only when the future looks like the past (steady growth), weaker for a new development and poor for a decline — they can't know about either.

Limits: this is a made-up corridor with our assumptions about model error; real studies can rank differently. The NCHRP standard remains the documented default reviewers expect; the others are there to compare and to explain your choice.
